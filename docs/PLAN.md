# ☕ 커피 내기 종합 게임 개발 계획서 (PLAN)

> 작성일: 2026-10-13 · 상태: 초안 (사용자 확인 필요 항목은 7장 참고)
> 표기: ✅ 권장/가능 · ❌ 비권장/불가 · ⚠️ 주의 · ⭐ 중요

## 1. 서비스 개요 / 목표

- **서비스명(가칭)**: 커피 내기 종합 게임 (repo: coffee game)
- **목적**: 사내 팀원끼리 커피값 낼 사람을 공정하고 재미있게 정하는 웹 프로그램
- **대상**: 사내 직원(비IT 직군 포함) → 설명 없이 바로 쓸 수 있는 쉬운 화면
- **핵심 목표**
  - ⭐ 참가자 이름 입력 → 게임 선택 → 결과 확인까지 **1분 이내**
  - 한 PC(회의실 화면, 노트북)에서 모두가 함께 보며 진행
  - 여러 게임 중 골라서 하는 "종합" 구성
  - (선택) 누가 몇 번 샀는지 기록·통계
- **범위 밖(MVP 제외)**: 로그인, 각자 휴대폰 동시 접속(실시간 동기화), 결제 연동

## 2. 게임 후보 목록

- 용어: **MVP** = 최소 기능 첫 버전(먼저 만들 핵심 묶음)
- 구현 난이도: 하(1~2일) / 중(3~4일) / 상(5일+) — 추정치

| 게임 | 방식 요약 | 재미 | 난이도 | 한 화면 진행 | MVP 포함 |
|---|---|---|---|---|---|
| 사다리타기 | 줄 따라 내려가 '당첨' 칸 확인 | ★★★★ | 중 | ✅ | ✅ 포함 |
| 룰렛 | 원판 돌려 멈춘 칸이 당첨 | ★★★★ | 하 | ✅ | ✅ 포함 |
| 제비뽑기 | 카드 뒤집기, 꽝/당첨 | ★★★ | 하 | ✅ | ✅ 포함 |
| 폭탄 돌리기 | 랜덤 시간 후 터질 때 차례인 사람 당첨 | ★★★★★ | 하~중 | ✅ (PC 돌려가며 클릭) | ✅ 포함 |
| 반응속도 | 신호 뜨면 클릭, 가장 느린 사람 당첨 | ★★★★ | 중 | ⚠️ 1명씩 순서대로 | 🔸 2차 |
| 핀볼/경마 레이스 | 말·공 랜덤 경주, 꼴찌 당첨 | ★★★★★ | 상 | ✅ | 🔸 2차 |
| 숫자 업다운 | 비밀 숫자를 돌아가며 맞힘 | ★★★ | 하 | ✅ | 🔸 2차 |

- **추천 MVP 4종**: 룰렛 · 제비뽑기 · 사다리타기 · 폭탄 돌리기
  - 이유: 운 요소 중심(실력 차 적음), 한 화면 진행 쉬움, 구현 부담 적음
- ⚠️ 반응속도는 실력 게임 → 매번 같은 사람이 질 수 있어 분위기 고려 필요

## 3. 공통 기능

| 기능 | 설명 | MVP |
|---|---|---|
| 참가자 입력 | 이름 추가/삭제, 최근 명단 불러오기 | ✅ |
| 당첨 인원 설정 | 1명 기본, 2명 이상 선택 가능 | ✅ |
| 게임 선택 | 카드형 목록, "랜덤 게임" 버튼 | ✅ |
| 결과 화면 | 당첨자 크게 표시, 다시하기 / 다른 게임 | ✅ |
| 효과음·애니메이션 | 긴장감 연출, 소리 켜기/끄기 | ✅ (간단 수준) |
| 기록(이력) | 날짜·게임·참가자·당첨자·메뉴/금액(선택) | ✅ |
| 통계 | 사람별 당첨 횟수, 게임별 사용 횟수 | 🔸 2차 |
| 벌칙 이력 | "커피 산 사람" 목록, 금액 합계 | 🔸 2차 |
| 공정성 옵션 | 최근 당첨자 확률 낮추기(연속 당첨 방지) | 🔸 2차 (기본 꺼짐) |
| BE 연결 설정 | BE 주소 입력 + "연결 테스트" 버튼 | 구조 B 선택 시 ✅ |

## 4. 구조 옵션 비교

- 용어: **FE** = 화면 / **BE** = 데이터 보관 서버 / **localStorage** = 브라우저 안 저장 공간 / **SQLite** = 파일 1개짜리 DB

| 항목 | A) FE 단독 (localStorage) | B) FE + BE + SQLite |
|---|---|---|
| 게임 진행 | ✅ 가능 | ✅ 가능 |
| 기록 저장 | ⚠️ 해당 PC·브라우저에만 | ✅ 서버에 저장 |
| 여러 PC 간 기록 공유 | ❌ 불가 | ✅ 가능 |
| 구현 기간 | 짧음 | +3~4일 |
| 운영 부담 | 없음 (GitHub Pages만) | BE PC 켜두기 + 터널 주소 갱신 |
| 장애 위험 | 낮음 | ⚠️ 터널 주소가 재시작마다 바뀜 |
| 데이터 백업 | JSON 내보내기/가져오기 | DB 파일 복사 |

- ⭐ **추천: A) FE 단독으로 시작 (BE 미사용)**
  - 게임 자체는 BE 불필요 (난수·애니메이션 모두 화면에서 처리)
  - 보통 한 PC에서 진행 → 기록도 그 PC에 쌓이면 충분
  - Cloudflare Quick Tunnel은 주소가 매번 바뀌어 비IT 사용자에게 번거로움
  - 기록 분실 대비: JSON 파일 내보내기/가져오기 제공
- **B 전환 조건**: "여러 PC/팀 통합 통계" 요구 확정 시 → Phase 7(선택)
  - 대비: 저장 로직을 `storage.ts` 한 곳에 모아 나중에 API로 교체만 하도록 설계

## 5. 화면 / 라우팅 구조

- 용어: **라우팅** = 주소(URL)별로 어떤 화면을 보여줄지 정하는 규칙

| 주소 | 화면 | 주요 요소 |
|---|---|---|
| `/` | 홈 | 참가자 입력, 당첨 인원, "게임 고르기" |
| `/games` | 게임 선택 | 게임 카드 목록, 랜덤 게임 |
| `/games/roulette` | 룰렛 | 원판, 돌리기 |
| `/games/lots` | 제비뽑기 | 카드 뒤집기 |
| `/games/ladder` | 사다리타기 | 사다리 그림, 출발 |
| `/games/bomb` | 폭탄 돌리기 | 폭탄, "넘기기", 숨김 타이머 |
| `/result` | 결과 | 당첨자, 메뉴/금액 메모, 다시하기 |
| `/history` | 기록 | 이력 표, 통계(2차), 내보내기/가져오기 |
| `/settings` | 설정 | 소리, 공정성 옵션, (B 시) BE 주소·연결 테스트 |

- 공통 레이아웃: 상단 메뉴(홈·게임·기록·설정), 큰 글씨·큰 버튼(회의실 화면 고려)
- 게임 공통 규칙: `참가자 목록 입력 → 당첨자 결과 출력` 형태 통일 → 새 게임 추가 쉬움

### 폴더 구성

| 폴더 | 용도 |
|---|---|
| `docs/` | 계획서, 사용 설명서 |
| `spec/` | 기능 명세(화면·게임 규칙) |
| `data/` | 샘플 명단, (B 시) SQLite 파일 |
| `project/frontend/` | Vite + TypeScript + React |
| `project/backend/` | FastAPI (B 선택 시에만) |
| `project/output/` | 내보낸 기록 파일 등 산출물 |
| 루트 | `start.bat` / `stop.bat` |

## 6. Phase별 로드맵

- 원칙: 단계마다 **테스트 후 커밋** · 단순하게 먼저, 꾸미기는 나중

| Phase | 내용 | 완료 기준(테스트) | 예상 |
|---|---|---|---|
| 0. 스캐폴드 | Vite+React+TS 생성, `start.bat`/`stop.bat` | start.bat → 빈 화면 표시, stop.bat 종료 | 0.5일 |
| 1. UI 뼈대 | 9개 화면 빈 틀, 상단 메뉴, 레이아웃 | 모든 메뉴 클릭 시 화면 이동 | 1일 |
| 2. 공통 기능 | 참가자 입력, 게임 선택, 결과, 추첨 로직 | 3명 입력 → 추첨 → 결과; 추첨 함수 단위 테스트 | 1일 |
| 3. MVP 게임 | 룰렛 → 제비뽑기 → 폭탄 → 사다리 | 1명·2명 당첨 확인 + 1,000회 분포 공정성 테스트 | 4~5일 |
| 4. 기록 | localStorage 저장, 이력 표, JSON 내보내기/가져오기 | 새로고침 후 유지, 재가져오기 성공 | 1일 |
| 5. 배포 | GitHub Pages 자동 배포(GitHub Actions), 사용 설명서 | 사내 PC 2대 이상 접속 확인 | 0.5일 |
| 6. (선택) 확장 | 2차 게임, 통계, 사내 디자인 적용 | 게임별 확인 | 필요 시 |
| 7. (선택) BE | FastAPI + SQLite, Quick Tunnel, BE 주소 입력·연결 버튼 | 두 PC에서 같은 기록 조회 | 3~4일 |

- MVP(Phase 0~5) 합계 추정: **약 8~9일** (1인 기준)
- 커밋 단위: Phase 1개 = 커밋 1개 이상
- ⚠️ Phase 7 주의: 터널 주소 재시작마다 변경, CORS(다른 주소 간 접근 허용) 설정 필요

## 8. 모호한 점 / 가정

- ⚠️ 최대 30명 → 룰렛 칸·사다리 줄이 촘촘해짐: 20명 초과 시 룰렛 글자 축소/번호 표시, 사다리 가로 스크롤 처리
- 📌 휴대폰 동시 참여 대비: 게임 로직을 화면과 분리(`참가자 → 결과` 순수 함수)해 향후 실시간 서버 연결 쉽게 설계

- ⚠️ "종합 게임" 범위(게임 개수) 미정 → MVP 4종으로 가정
- ⚠️ 사내 보안 정책(외부 배포·터널 허용) 미확인
- ⚠️ 일정은 1인 기준 대략치, 애니메이션 완성도에 따라 변동
- ⚠️ 휴대폰 참여 요구 확정 시 구조 재설계 필요(실시간 통신) → 현재 범위 밖
